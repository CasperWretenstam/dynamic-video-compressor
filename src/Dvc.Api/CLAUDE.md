# Dvc.Api

The web API. See the root `CLAUDE.md` for the repo as a whole (commands, git workflow, shared conventions, the FFmpeg dependency) and `src/Dvc.Core/CLAUDE.md` for the compression engine this project runs: the parameter philosophy, `TargetSizeBytes` vs `QualityPreference`, the encode modes and the math. Paths below are relative to `src/Dvc.Api/`.

## What this is

An ASP.NET Core Web API that compresses video files with `Dvc.Core`, designed as a microservice sitting downstream of an upload system: a caller (e.g. a website's backend) posts a video directly to it and polls for a compressed result, rather than the end user touching this service directly. It adds everything around the engine: the HTTP contract, a job queue and database, config, and the Docker image.

This file documents the local, non-Docker `dotnet` workflow except where "Containerized deployment" says otherwise; `docker compose up -d --build` runs it with FFmpeg bundled (see the root `README.md`).

## Commands

Run the API: `dotnet run --project src/Dvc.Api` (binds `http://localhost:5155`; add `--launch-profile https` for the HTTPS profile too). `ASPNETCORE_ENVIRONMENT=Development` is set via `launchSettings.json`, not the shell.

Add a migration: `dotnet ef migrations add <Name> --project src/Dvc.Api --output-dir Infrastructure/Data/Migrations` — the `--output-dir` flag is required; without it EF Core creates a new top-level `Migrations/` folder instead of using the existing `Infrastructure/Data/Migrations/` location.

Apply migrations: `dotnet ef database update --project src/Dvc.Api`

## Request lifecycle

`POST /v1/jobs` (multipart) → `202 Accepted` with a job ID, immediately, without waiting on FFmpeg → caller polls `GET /v1/jobs/{id}` for status → once `Completed`, `GET /v1/jobs/{id}/result` streams the compressed file back → the caller cleans up with `DELETE /v1/jobs/{id}`. `GET /v1/options` describes every job parameter for clients (see "Parameter philosophy" in `src/Dvc.Core/CLAUDE.md`). The job and options endpoints are mapped under a `/v1` route group in `Program.cs` (their own `Map*Endpoints` methods use unprefixed paths); `/health`, `/openapi` and `/scalar` stay unversioned, since they describe the deployment rather than the API contract. A breaking change ships as a new `/v2` group alongside, not as an edit to `/v1`.

- **`Endpoints/JobEndpoints.cs`** — Minimal API (chosen deliberately over controllers). The file holds the route mappings and handlers, with the few private helpers they use after them; anything larger lives in its own class, so each handler reads top to bottom. `SubmitJob` hands the multipart body to `JobUploadReader` (below), passes the resulting `SubmitJobRequest` to `JobSubmissionService`, and returns `202`. If the submission fails, it deletes the upload, since no job will consume it.
- **`Endpoints/JobUploadReader.cs`** — reads the `POST /v1/jobs` body and returns a `JobUploadResult`: either a validated `SubmitJobRequest`, with the video already written to `Storage/Input`, or the problem response to return instead. It hand-parses the multipart body with `MultipartReader` rather than binding `[FromForm] IFormFile`: the built-in form binder buffers the whole upload to a temp file before the handler runs and then copies it again into `Storage/Input`, so parsing it directly and streaming the file section straight to its final path skips that redundant copy. It validates, at the API boundary (`400` rather than an async failure), only what could never produce an encode or would be silently lost: an unknown or repeated field name (matched ignoring case, so `Resolution` and `resolution` count as a repeat, and checked before its value is read, so a blank one is rejected too), the file extension against `VideoFileDefinitions.SupportedExtensions`, unparseable numbers, a `TargetSizeBytes` that isn't a whole number, `TargetSizeBytes`/`Fps` ≤ 0, and `QualityPreference`/`Resolution`/`EncoderPreset` against their `Dvc.Core` `Definitions` tables — before `SubmitJob` hands off to `JobSubmissionService`. Every check runs as early as the body allows, since sections are handled in the order the client sends them: a declared `Content-Length` over `UploadDefinitions.MaxUploadBytes` gets `413` before any of the body is read (a chunked body hitting Kestrel's limit mid-stream gets the same `413`), the extension is checked before the file streams, and each field is validated as soon as it's read — so a client sending its fields before the file (the documented order, and what the `scripts/` do) never uploads a video a bad field would reject. All checks are per-field; there's no cross-field validation that would need the whole body first. Numbers parse with the invariant culture, so `29.97` works regardless of server locale. An empty field value counts as not set (forms send blank inputs that way), and `QualityPreference`/`Resolution`/`EncoderPreset` are matched case-insensitively but stored in their table's own spelling (`CanonicalKey`), since the preset goes straight to ffmpeg and all three are echoed back in job status. A second file part is rejected. Any rejection, oversized or aborted upload deletes whatever it had written so far in one `finally`; on success the caller owns the file.
  `DeleteJob` (`DELETE /v1/jobs/{id}`) removes the row, then the job's input and output files. A `Queued` job is cancelled this way; a `Processing` one gets `409`, since there's no way to stop an encode partway through. The delete is a conditional `ExecuteDeleteAsync` matching the status just read, and the worker claims a job with a conditional `ExecuteUpdateAsync` (`Queued` → `Processing`). Whichever commits first wins: either the worker finds no `Queued` row and skips the ID, or the delete matches nothing, re-reads, and sees `Processing`. A file that can't be deleted once the row is gone (e.g. the result still being streamed, on Windows) is logged rather than failing the request.
- **`Endpoints/OptionsEndpoints.cs`** — `GET /v1/options`: a machine-readable description of every `POST /v1/jobs` parameter (level, type, allowed values with descriptions, default), built from the same `Dvc.Core` `Definitions` tables and `EncodingOptions` the pipeline uses so it can't drift from actual behavior. Meant for clients to build their UI from. When adding a job parameter, add it here too — `OptionsEndpointsTests` reads `SubmitJobRequest`'s properties (minus the server-set `InputPath`/`OriginalFileName`/`FileSizeBytes`) and fails on any that isn't described. A parameter described here also reaches the OpenAPI document's upload form automatically (see "OpenAPI document" below).
- **`Services/JobSubmissionService`** — creates the `Job` row as `Queued` (deciding whether the job is driven by `TargetSizeBytes` or `QualityPreference` — see "Job warnings and errors" below — and resolving an unset `EncoderPreset` from `Encoding:Preset`, so the job keeps the preset it was queued with), saves it, then hands the job ID to `IJobQueue.Enqueue` and returns. All actual compression happens out-of-band in `JobProcessingWorker`.
- **`Infrastructure/JobQueue.cs`** — an unbounded, single-reader `Channel<Guid>` (many concurrent `POST /v1/jobs` writers, one background reader). In-memory only — it does not survive a restart, which is why `Program.cs` re-enqueues anything left `Queued`/`Processing` at startup (see "Config" below).
- **`Infrastructure/JobProcessingWorker.cs`** — the registered `BackgroundService` that drains the channel in a single sequential `await foreach` loop, so jobs are guaranteed to complete in the order they were submitted. A dequeued ID whose row is no longer `Queued` (deleted while waiting) is skipped. It owns the output path (`Storage/Output/{id}.mp4`), persisting it as `Job.OutputPath` together with `Processing` — in the same conditional update that claims the job — *before* encoding starts, so startup recovery always knows which partial file to discard. Catches and logs per-job failures (marking the `Job` row `Failed` with `ErrorMessage`, deleting whatever partial output ffmpeg wrote, and clearing `OutputPath`) without killing the loop, so one bad job doesn't stall the queue. Once a job finishes (success or failure), its `Storage/Input` file is deleted — it's fully consumed by ffprobe/ffmpeg by then, and a failed job has no retry concept (a caller resubmits fresh rather than the service reusing the upload). A shutdown mid-encode is deliberately *not* a failure: whatever the cancelled encode throws, the row stays `Processing` with its input intact and the loop exits, leaving startup recovery to re-run it. Once an encode has finished, its outcome is saved with `CancellationToken.None`, so a shutdown landing then doesn't throw away a finished result.
  It's also the bridge to `Dvc.Core`: it builds a `CompressionRequest` from the `Job` and `EncodingOptions` (mapping the `Resolution` label to its short side in pixels with `ResolutionDefinitions.ShortSides`, and filling `TwoPass` and the default caps from config), runs probe → `PlanOutput` → `PlanEncode` → `EncodeAsync`, and writes the results back onto the `Job`. The output dimensions are saved before `PlanEncode`, which can throw, so a job that fails planning still shows what it attempted; plan warnings (the cap at the source's bitrate) are appended before encoding, after any warning from submission, so they survive a failed encode; the encode's own warnings only exist on success. Each job runs inside a `logger.BeginScope("Job {JobId}", …)`, and `Program.cs` turns on `IncludeScopes`, so `Dvc.Core`'s log lines, which never mention jobs, still show which job they belong to.
- **`Models/Definitions/UploadDefinitions`** — the API-only upload size limit (`MaxUploadBytes`, 2GB, shared by Kestrel and `SubmitJob`).
- **`Infrastructure/Data/DvcDbContext`** — EF Core + SQLite, a single `Jobs` table.
- **`Endpoints/HealthEndpoints.cs`** — `GET /health`: liveness only (confirms the process is up and responding), not a dependency check of the database or storage. Exists to back the `Dockerfile`'s `HEALTHCHECK`; a deeper readiness check is a separate concern that hasn't been needed yet.

### Job warnings and errors

A job is driven by exactly one of `TargetSizeBytes` and `QualityPreference` (or its default, `Balanced`, if the caller sends neither), decided by `JobSubmissionService`. If a caller sends both, `TargetSizeBytes` wins and `JobSubmissionService` records a `Job.Warning` that `QualityPreference` was ignored.

`Job.Warning` is distinct from `Job.ErrorMessage`: a warning means the job still completed, just not exactly as requested (a submission warning, or `Dvc.Core`'s plan and encode warnings: a `TargetSizeBytes` bitrate was capped at the source's bitrate, or output size initially overshot but corrected); an error means the job failed outright (including a `TargetSizeBytes` that couldn't be hit even after the corrective re-encodes).

`ErrorMessage` is written for the caller, who may show it to end users. Only a `Dvc.Core` `CompressionFailedException`'s message reaches it. Every other exception gets a generic message in `JobProcessingWorker`, because it's mostly FFMpegCore relaying ffmpeg's raw output, banner and build configuration included. The full exception is still logged.

### Data model

- **`Models/Entities`** (`Job`, `JobStatus`) vs **`Models/DTOs`** (`SubmitJobRequest`) — kept separate on purpose: binding the multipart request directly to `Job` would let a caller set fields like `Id`, `Status`, or `OutputPath` that should only ever be set server-side. `JobUploadReader` populates `SubmitJobRequest` by hand from the parsed multipart sections.
- `Job.Resolution`/`Fps` are null when the caller didn't set them (resolved from the source at compression time); `Job.EncoderPreset` is always set (resolved from config at submission). `Job.OutputWidth`/`OutputHeight`/`OutputFps` record what the output actually resolved to — set by `JobProcessingWorker` from `CompressionPlanner.PlanOutput` once the source is probed, so they're persisted even for a job that then fails, and cleared by startup recovery when a mid-encode job is reset to `Queued`.
- `GET /v1/jobs/{id}` returns `Models/DTOs/Responses/JobStatusResponse`: `settings` (what the job was submitted with, null `resolution`/`fps` meaning "follow the source") and `output` (the resolved dimensions/fps, null until processing has probed the source).
- `JobStatus` is `Queued` → `Processing` → `Completed` | `Failed`.
- Enums are serialized by name in JSON responses (e.g. `"status": "Completed"`), via a global `JsonStringEnumConverter` registered with `ConfigureHttpJsonOptions` in `Program.cs`. The database still stores them as integers — this only affects the HTTP boundary, so no migration is involved.

### OpenAPI document

`/openapi/v1.json` is generated from endpoint metadata at startup, never by running a handler, so each endpoint has to declare what it returns:

- **Return types.** Handlers return precise typed results (`Results<Ok<JobStatusResponse>, ProblemHttpResult>`, `Ok<JobOptionsResponse>`, …), never `IResult`: each typed result adds its status code and schema to the document, and the compiler rejects a `return` the declared type doesn't list. `POST /v1/jobs` returns `Models/DTOs/Responses/JobSubmittedResponse`, so its `202` body has a named schema.
- **Errors.** A `ProblemHttpResult` can't declare its status code (it's chosen at runtime), so each endpoint lists every status it returns with `.ProducesProblem(...)` next to its `.WithName(...)`, and the `/v1` group in `Program.cs` adds `500` for unhandled exceptions. Nothing checks these against the handler, so keep them in sync by hand when adding or removing an error.
- **The download** declares `.Produces<Stream>(…, "video/mp4")` for `200` and `206` (range requests), since a file result declares no content type.
- **Descriptions.** `GenerateDocumentationFile` is on, and .NET 10's OpenAPI generator turns XML doc comments into the document's descriptions at compile time. On a handler, `<summary>` becomes the operation's title, `<remarks>` its description, `<param>` a route parameter's description and `<response code="…">` that status code's description. On a model, `<summary>` becomes the schema's description, and `<summary>` on a property (or `<param>` on a record's positional property) the property's; `<remarks>` on a model isn't included. Two things follow: handlers must be `internal`, since the generator ignores comments on `private` methods, and every endpoint is a named method in an `Endpoints/*Endpoints` class, since a lambda can't carry doc comments (hence `HealthEndpoints`). `ProblemDetails` and the download's `Stream` are framework types and stay undescribed: the framework's own XML docs for `ProblemDetails` cite the obsolete RFC 7807 and come through with raw `<see href>` tags.
- **The upload form.** `SubmitJob`'s body is parsed by hand (`JobUploadReader`), so there's nothing for the generator to infer. A per-endpoint `.AddOpenApiOperationTransformer(...)` sets the request body from `Infrastructure/OpenApi/JobFormSchema`, which maps `OptionsEndpoints.BuildJobOptions` (the same parameter descriptions `GET /v1/options` returns, with the configured defaults) to a `multipart/form-data` schema: allowed values as `enum` (their descriptions folded into the field's Markdown description, since JSON Schema can't describe enum values individually), numbers (and `int64` integers, for a `ParameterType.Integer` field such as `TargetSizeBytes`) with `exclusiveMinimum: 0`, `additionalProperties: false`, and the file listed last, matching the fields-before-file order `JobUploadReader` validates in. `JobFormSchemaTests` covers the mapping.

`/scalar` (the `Scalar.AspNetCore` package's `MapScalarApiReference()`) is an interactive reference built from this document, where testers can submit a video, poll the job and download the result from the browser. It has no configuration of its own: whatever the document describes is what it shows, so the upload form above is what makes submitting from it work.

Both are mapped only when `OpenApi:Enabled` is on (see "Config").

## Conventions

The root `CLAUDE.md` has the conventions shared by every project; these are specific to the API.

- `DvcDbContext` is registered scoped (`AddDbContext`). Anything registered as a singleton must not take it as a constructor dependency directly — resolve it per unit of work via `IServiceScopeFactory` instead. `JobProcessingWorker` (a singleton-lifetime hosted service) follows this: it takes `IServiceScopeFactory` and creates a scope per job.
- **Docs that reach the API document are written for callers.** That's the endpoint handlers and the types the endpoints return: `Models/DTOs/Responses` and `JobStatus` (see "OpenAPI document" for which tags are included). Say what an operation or field means for the caller's result, not how the code produces it. Reasoning a developer needs goes in `<remarks>` on a model, which the document leaves out (if a later generator includes it, that's acceptable), or in a `//` comment on a handler, where `<remarks>` is the operation's public description. `SubmitJobRequest` and the entity `Job` never reach the document, so they're written for developers.
- **Handler and model tags:** a handler's `<summary>` is a short operation title with no closing period ("Get a job's status"), since Scalar shows it as one; its `<remarks>` says what the operation does, and each status code it returns gets a `<response>`. A model whose fields reach the API document gets a description on every property, so no field shows up unexplained.

## Config

- `appsettings.json` holds baseline config (DB connection string, `Database:AutoMigrate`, `Storage:InputDirectory`/`OutputDirectory`, the `Encoding` section and `OpenApi:Enabled`), listing every setting the service reads with its default, and ships in the build output regardless of environment. `launchSettings.json` is dev-machine-only and never published — it's what sets `ASPNETCORE_ENVIRONMENT=Development` locally, which is what causes `appsettings.Development.json` to layer on top.
- The `Encoding` section binds to `Models/Options/EncodingOptions` (`TwoPass`, `Preset`, `DefaultMaxShortSide`, `DefaultMaxFps`) via the options pattern, validated with `ValidateOnStart` so a bad preset or non-positive cap stops startup instead of failing jobs. An empty cap value (`"DefaultMaxShortSide": ""`, or `Encoding__DefaultMaxShortSide=` as an env var) binds to null and disables that cap. Other config (`Database:AutoMigrate`, `OpenApi:Enabled`, `Storage:*`) is still read ad hoc via `IConfiguration`.
- `Program.cs` raises Kestrel's request body limit to `UploadDefinitions.MaxUploadBytes` (2GB; default ~30MB is far too low for real video uploads) and caps `MaxConcurrentConnections` at 100 — a coarse whole-server failsafe against a runaway/misbehaving caller, not a real rate limiter (that belongs in the client-facing service upstream of this one).
- On startup, `Program.cs` sets the SQLite database to WAL journal mode + `synchronous=NORMAL`, so status polling (`GetJobStatus`) can proceed without blocking on the background worker's writes. `journal_mode` is stored in the database file itself, so this is a no-op after the first run.
- Also on startup, before the host starts `JobProcessingWorker`, `Program.cs` recovers jobs an unclean shutdown left mid-flight: any `Job` still `Queued` was lost from `JobQueue`'s in-memory channel (it doesn't survive a restart) and needs re-enqueuing; any `Job` stuck `Processing` was killed mid-encode, so its `OutputPath` (persisted by `JobProcessingWorker` before encoding starts) is partial/corrupt and gets deleted before it's reset to `Queued` and re-run from scratch. Both are re-enqueued in `CreatedAt` order (ordered client-side — SQLite can't translate `ORDER BY` on `DateTimeOffset` server-side via EF Core).
- Every error response is problem details (RFC 9457, `application/problem+json`). Endpoints return them with `TypedResults.Problem`, always with the message in `detail` (the shared `Endpoints/ProblemResults` helpers `Problem`/`BadRequest`). `AddProblemDetails()` + `UseExceptionHandler()` cover unhandled exceptions, and `UseStatusCodePages()` covers framework errors with no body, such as an unknown route or a wrong HTTP method. Logging goes through `AddSimpleConsole` with single-line, UTC-timestamped output, with `IncludeScopes` on so the worker's per-job scope (`=> Job <id>`) prefixes every line logged while a job runs.
- `Database:AutoMigrate` (default `false` in `appsettings.json`, with the same `false` as a code fallback if the entry is removed; read ad hoc via `IConfiguration` rather than an options class) runs `Database.Migrate()` at startup when set. Off by default so local `dotnet run` development keeps requiring an explicit `dotnet ef database update` (see "Runtime data" below); the `Dockerfile` sets it to `true` as an `ENV` default, since there's no `dotnet-ef` tool available in a slim runtime container to run migrations separately. Runs before the orphaned-job recovery block, which queries the `Jobs` table and would fail against a schema-less database.
- `OpenApi:Enabled` (default `false`, read ad hoc via `IConfiguration`) maps `/openapi/v1.json` and `/scalar` (see "OpenAPI document"). `appsettings.Development.json` turns it on, so a local `dotnet run` serves them. Everywhere else it's an explicit opt-in, including the Docker image, which runs as Production: an operator sets `OpenApi__Enabled=true`, e.g. in `docker-compose.yml`. It's a switch of its own rather than an `IsDevelopment()` check so a deployment can turn the docs on without switching to the Development environment, which would also load `appsettings.Development.json`. Neither endpoint exposes anything `GET /v1/options` doesn't already describe, so turning them on adds no real exposure; the service's lack of auth (see "Known gaps") is the real boundary.

## Runtime data (not committed)

`dvc.db` (+ its `-wal`/`-shm` files) and `Storage/` (uploaded/output video files) are both gitignored — local runtime state, not source. `dvc.db` resolves relative to the app's working directory, which for `dotnet run --project src/Dvc.Api` is the project folder, so it lives at `src/Dvc.Api/dvc.db`. Migration-on-startup is off by default (see `Database:AutoMigrate` in "Config" above), so a fresh or deleted `dvc.db` needs an explicit `dotnet ef database update` before the app can persist a `Job` — the Docker image is the exception, since it turns `Database:AutoMigrate` on.

## Dev scripts

`scripts/` (at the repo root) holds PowerShell tooling for checking and poking at a running instance. Everything runs on both Windows PowerShell 5.1 and PowerShell 7+ (so also on Linux/macOS), which rules out 7-only syntax (`??`, ternaries, `&&`) and `Invoke-RestMethod -Form`. Keep the files ASCII-only too: 5.1 reads a BOM-less script as the system codepage.

- `DvcScripts.psm1` — the shared module every script imports; all API calls, clip generation and output styling go through it, so each script is a thin wrapper. Functions use approved verbs with a `Dvc` noun prefix: `Connect-DvcService` (checks `/health` and sets the base URL for the session), `Submit-DvcJob`, `Get-DvcJob`, `Wait-DvcJob`, `Save-DvcJobResult`, `Remove-DvcJob`, `Invoke-DvcRequest` (returns status/body without throwing, for checking expected errors), `New-DvcJobContent`, `New-DvcTestClip`, `Get-DvcVideoInfo` (ffprobe), `Write-DvcStatus` (the shared `[ OK ]`/`[FAIL]` line style). HTTP goes through one `HttpClient` rather than `Invoke-RestMethod`, whose multipart and error handling differ between 5.1 and 7. Test clips are encoded with `mpeg4`/`aac`, which every ffmpeg build has, so the scripts don't need a libx264 build locally.
- `Test-Setup.ps1` — the install check the README points users to. HTTP only, so it works against Docker, local or remote (`-BaseUrl`). Submits default, `TargetSizeBytes`, explicit `Resolution`/`Fps`/`EncoderPreset` (sent as camelCase names, to cover case-insensitive matching), silent and video-less clips back to back. Checks each outcome, that a `TargetSizeBytes` result is under target, `400` rejections (including an unknown field and a repeated one), completion order (`JobProcessingWorker`'s sequential-drain guarantee), and `DELETE` for both a queued and a finished job. Deletes everything it created unless `-KeepJobs`, and exits non-zero on any failed check.
- `Submit-TestJob.ps1` — submits one job with whichever parameters are passed, sent exactly as given (including conflicting ones). With no `-FilePath` it generates a clip. `-Wait`, `-OutFile` and `-Remove` optionally wait, download and delete.
- `Show-Jobs.ps1` — local dev only: dumps the `Jobs` table from `dvc.db` via `sqlite3` (`-Last N` for the newest few). Safe against a live DB since it's WAL mode.
- `Reset-DevData.ps1` — local dev only: wipes `dvc.db` and everything in `Storage/Input`/`Storage/Output`, then re-applies migrations. Refuses to run while `Dvc.Api` is running (the DB file would be locked) unless `-Force` is passed.

## Tests

`tests/Dvc.Api.Tests` covers `EncodingOptions` binding (including empty-disables-cap), `JobStatusResponse.FromJob`, `OptionsEndpoints.BuildJobOptions`, the OpenAPI upload form (`JobFormSchema`) and the multipart parsing in `JobUploadReader` — unit tests with no I/O beyond a temp directory (`JobUploadReaderTests` feeds hand-built multipart bodies through a `DefaultHttpContext`), no ASP.NET/EF/FFmpeg integration tests exist yet. When adding coverage for the request pipeline, endpoints, or the worker, a new test project or fixture will be needed (nothing currently spins up the app in-memory). The natural next step is `WebApplicationFactory<Program>` integration tests that submit a tiny ffmpeg-generated clip (as the `scripts/` do) and poll it through — they'd need real `ffmpeg`/`ffprobe` on PATH, so probably as a separate test category that a plain `dotnet test` run can skip. Until then, `scripts/Test-Setup.ps1` is the end-to-end check: it covers `400` rejections, a failing job, queue order and `DELETE` against a running instance. `JobUploadReaderTests` covers the early `413` and deleting a rejected upload; the delete/claim race and shutdown recovery are still verified only by hand.

## Containerized deployment

`Dockerfile` (multi-stage: `dotnet publish` in an SDK stage, then a slim `aspnet` runtime stage) + `docker-compose.yml`, both at the repo root, bundle FFmpeg and the .NET runtime together — see the root `README.md` for usage. Things worth knowing if touching either file:

- FFmpeg comes from `mwader/static-ffmpeg`, copied into the final image via multi-stage `COPY --from=`, rather than an `apt-get install ffmpeg`. Debian's own `ffmpeg` apt package does **not** include libx264 (verified against packages.debian.org's listed dependencies) — only Ubuntu's build or a purpose-built static binary does, and `static-ffmpeg` sidesteps needing to switch base images or add a non-free repo just for this.
- The container runs as the base image's non-root `app` user (`USER $APP_UID`, UID 1654), so everything it writes must live under `/data`, which the image creates owned by that user. The `Dockerfile`'s `ENV` defaults point the database and `Storage/` there, so the image works with or without compose. Overriding them to a path outside `/data` would fail on the first write, since the app's working directory `/app` is root-owned. A volume created by an earlier root-run container keeps root ownership and needs a one-off `chown -R 1654 /data`.
- All container defaults (the `/data` paths, `Database:AutoMigrate`) live in the `Dockerfile`; `docker-compose.yml` only maps the port and the volume, plus any overrides a deployer adds.
- The health check lives only in the `Dockerfile`, so it also applies to a plain `docker run`.
- The build stage copies every project's `.csproj` (`Dvc.Api` and the `Dvc.Core` it references) before `dotnet restore`, then their sources, so the restore layer stays cached until a project file changes. A new project the API references needs adding to both steps.

## Known gaps

- **No automatic output retention.** A job's row and `Storage/Output` file are removed only when the caller sends `DELETE /v1/jobs/{id}`. Nothing expires them, so a caller that never deletes slowly fills the disk. A TTL sweep would be the backstop for that; it's deliberately deferred, since it needs a retention-window decision. `Storage/Input` is not part of this gap — those are deleted as soon as each job finishes (see `JobProcessingWorker` above).
- **No disk-space or queue-depth guard.** `JobQueue` is unbounded and nothing checks free space before accepting an upload or starting an encode, so a burst of large uploads can fill the disk (`Storage/Input` up to 2GB per job while queued, plus each output). Acceptable behind a single trusted caller; a queue cap is planned (see "Planned features" below), and a free-space check in `SubmitJob` (`503` when below a threshold) would complement it.
- **No auth/authorization** on the endpoints — acceptable only insofar as the service is never exposed directly to end users, per "What this is" above; still a gap if it's ever reachable other than from a trusted caller.

## Planned features

Job priority and the queue cap are aimed at callers backfilling an existing library (mass-compressing stored files to free space) through the same `POST /v1/jobs` as live uploads, without stalling those uploads. Orchestrating the backfill itself (walking the caller's database, fetching from and swapping files back into their storage) stays the caller's job, since it depends on their schema and storage; at most a reference feeder script could ship alongside the `scripts/`.

- **Job priority.** An optional `Priority` field on `POST /v1/jobs` (e.g. `Normal`, the default, and `Background`). The worker always takes the oldest `Normal` job before any `Background` one, keeping first-in, first-out order within each priority. This replaces `JobQueue`'s single FIFO channel (two channels, or picking the next job from the database), and startup recovery must re-enqueue by the same rule. No preemption: a `Background` encode already running finishes before a new `Normal` job starts. Additive, so it fits within `/v1`; add it to `GET /v1/options` too.
- **Queue cap.** Reject submissions with `503` once the queue is full, so a backfill feeder that submits too fast gets backpressure instead of filling the disk. Undecided whether the cap counts `Queued` jobs or their total queued input size; size tracks the actual disk risk (`Storage/Input` holds each queued upload until its turn) better than a count. Likely applied to `Background` jobs, or with a separate limit for them, so a backfill can't block live uploads from being accepted.

Custom output resolution (an explicit width × height) is planned too; most of its changes land in the engine, so it's described under "Planned features" in `src/Dvc.Core/CLAUDE.md`, including the API's part.
